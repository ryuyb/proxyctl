## 2. 分能力详述

### 2.1 明确「不重复实现」的能力

| 能力 | 由谁提供 | 我们的做法 | 依据 |
|---|---|---|---|
| 代理协议与转发 | **Mihomo** | 只做生命周期与配置，不碰协议实现 | R01 |
| Dashboard 交互（代理组/连接/日志/规则） | **metacubexd** | 内嵌其静态产物 + 同源 Clash API 反代；不修改其代码 | R07 |
| 订阅转换引擎（节点解析/过滤/重命名） | **Sub-Store** | 通过 `SubscriptionConverter` Port 调用；可选外部组件 | R04、R05 |
| TUN/路由/nftables 的内核侧实现 | **Mihomo / Linux 内核** | 只做**检测**与（后续）规则编排，不重写数据通路 | R11 |
| 内核二进制本身 | **Mihomo 上游** | 只做下载/校验/替换/回滚 | R01、R13 |

### 2.2 必须由我们负责的能力（核心价值）

| 能力 | 为什么现有项目不够 | 依据 |
|---|---|---|
| **配置版本库（不可变 + checksum + 来源 + 历史）** | metacubexd 只有单槽 `.bak`；ShellCrash 只有 `config.yaml.bak`；竞品无 `list/show/diff/activate/rollback` | R07、R08、R15 |
| **原子激活 + 失败回滚（reload/健康检查失败即回退）** | 上游 reload 是"先解析后应用"（好），但**没有**"激活后健康检查失败自动回滚"的编排；ShellCrash 是"自启锁死" | R01、R08、R15 |
| **PVE LXC 能力检测与显式降级** | ShellCrash 只有 `systype='container'` 布尔判断；无 unprivileged/CAP/`/dev/net/tun` 实现级检测 | R08、R10 |
| **Doctor 能力分层（五值状态）** | 无任何项目做 LXC/容器能力分层；全行业用 bool | R10、R15 |
| **统一 Use Case（CLI/TUI/Web 同一业务入口）** | 竞品多为单一前端；多端会出现行为漂移 | R15 |
| **最小权限与审计** | ShellCrash `uid 0 + 独立 gid` 是假隔离；Sub-Store 无认证 | R08、R12 |
| **内核更新与配置更新彻底分离** | ShellCrash 混在一起；metacubexd desktop 也把内核与运行绑定 | R08、R07 |

### 2.3 能力状态模型（我们的差异化语义）

```text
Supported      该能力在当前环境已具备且被验证可用
Unsupported    当前实现不支持（例如 MVP 不做的 TProxy 自动配置）
Unavailable    环境不具备（例如无 CAP_NET_ADMIN）
Misconfigured  具备前置条件但配置/权限有误（例如有 /dev/net/tun 但 TUNSETIFF 返回 EPERM）
Unknown        尚未探测或探测失败
```

**关键实测依据**：`/dev/net/tun` **存在且可 `open()`** 仍可能在 `ioctl(TUNSETIFF)` 返回 `EPERM`（R10 实测）→ 因此"设备存在"绝不能被当作 `Supported`，必须区分 `Misconfigured`。

## 3. 结论

1. **"管理 Mihomo"本身不构成差异化**——metacubexd 的 agent、ShellCrash、mihari 等已覆盖大半（R07、R08、R15）。
2. **我们的差异集中在**：不可变配置版本库 + 原子回滚、PVE LXC 能力分层检测与降级、Doctor 五值状态、统一 Use Case、可替换转换器、最小权限与审计（R15 明确这些是空白）。
3. **所有下游实现必须尊重**：`Mihomo`(GPL-3.0)/`Sub-Store`(AGPL-3.0) 只能以**独立进程 + API 调用**方式使用，不得内嵌源码（R13）。
